# 🎋 絶望えらぁ短歌 (Zetsubou Tanka)

> **プログラミングのエラーログと怨念を、風流で悲痛な「短歌」へと昇華するエンタメ系Webアプリケーション。**
> <https://despair-tanka.onrender.com/>

---

## 1. サービス概要

エラーログやクソコードを入力すると、AI（OpenAI API）がその悲惨さと絶望感を和風モダンの「短歌（5・7・5・7・7）」へと変換して詠み上げ、さらに縦書きの美しいOGP画像として即座にX（旧Twitter）でシェアできるWebサービスです。

エラーメッセージの解読に疲弊し、モチベーションが削がれた初学者エンジニアの「孤独感・ストレス」を、自虐と共感を誘う短歌生成・お焚き上げ・おみくじ・展覧会（Gallery）・縦書き動的OGP画像生成を通じて「笑いと癒やし」へと変えて解消します。

| 項目 | 内容 |
| :--- | :--- |
| **誰** | エラーログと格闘中の初学者・若手エンジニア（20〜30代、独学・スクール生・リモート勤務） |
| **どんな課題** | エラーによる挫折感・「自分だけができない」という孤独感から精神的ストレスを抱え、開発の足が止まってしまう |
| **どう解決** | エラーログを即座に「風流な短歌」へ変換。縦書きOGP画像としてXでシェア・共感（いいね）を集めることで、絶望を笑いと自己表現のアートに変える |

---

## 2. アイデアの背景

開発のきっかけは、卒業制作でつまずいていたスクールの先輩を応援していたときの体験です。

画面共有越しに見せてもらった真っ赤なエラーログと、それに苦しむ先輩の姿を見たとき、「なんとか力になりたい」と強く思いました。しかし当時はまだ入学して日が浅く、自分の技術力ではエラーの根本原因を即座に解決してあげることはできず、「ただ応援することしかできない」という強いもどかしさを感じました。

エラーログは言わばエンジニアの悲鳴です。技術で直接助けられなくても、

> 「この悲惨な空気や切なさを、いっときでも『笑い』に変えて場を和ませることはできないか」
> 「風流な『短歌（辞世の句）』にしてネタ化してしまえば、辛いエラーとの戦いもユーモアあるアートになるのではないか」

と思いついたのが開発のスタートです。エラーでつまずくことはエンジニアなら誰もが通る道ですが、直面している最中は「自分だけができないんじゃないか」「時間が溶けていく…」と孤独になりがちです。プログラミングの辛さをそのまま愚痴として吐き出すのではなく、日本伝統の「短歌」に乗せることで、絶望をユーモアや風流なアートに変えて共有できたら、身近な仲間はもちろん、自分を含めた多くの学習者が救われる——そう考え、このコンセプトに強い可能性を感じました。

**「自分自身」および「身近な学習仲間（スクール同期・先輩）」**が想定ユーザーであり、現在進行形で自分自身がエラーログと格闘しているからこそ、ユーザーの痛みを100%理解できる「N=1」のリアルな体験に基づいて作られています。

## 3. 課題の整理（5 Whys）

| # | 問い | 答え |
| :-- | :--- | :--- |
| Q1 | なぜエラー文を見るとモチベーションが下がるのか？ | エラーの原因が判明せず、一人で画面に向かい続けるのが精神的に辛いから |
| Q2 | なぜ一人で画面に向かい続けるのが辛いのか？ | 自分の技術不足を感じ、「時間が無駄になっている」という孤独感や徒労感に苛まれるから |
| Q3 | なぜ孤独感や徒労感を抱えてしまうのか？ | 開発中の失敗やエラーの辛さを、気軽に・楽しく人に共有できる場がないから |
| Q4 | なぜ気軽に共有できないのか？ | 単なる愚痴やネガティブなつぶやきは投稿しづらく、周囲に心配やネガティブな印象を与えてしまうから |
| Q5 | なぜネガティブな感情を「短歌」に変える必要があるのか？ | ユーモアと風流な形に昇華することで、失敗を「ネタ（自虐アート）」として開示でき、「みんな同じように苦しんでいる」という共感と自己許容（心理的安全）を得られるから |

> **💡 本当に解決したい課題**
> エラーに対する「絶望感・孤独感」を、自虐と共感のエンタメ体験に変え、エンジニアが挫折せずに前を向いて学習を続けられる環境を作ること。

## 4. 想定ユーザーと利用の流れ

**属性**：Webエンジニアを目指してスクールや独学で勉強中の初学者、または若手エンジニア（20代〜30代）

**利用場面**：

- 日夜コードを書き、エラーログの赤文字と戦って心が折れそうな瞬間
- 「今日はエラーで進まなかった…」という日の終わりに、感情を整理したい時

**利用環境**：独学やリモート学習で相談相手が近くにいない環境。展覧会（Gallery）でお互いの絶望短歌を見ることで「みんな苦しんでいる」と共感し合える環境。

```text
[認知]   Xで流れてきた縦書きの「絶望短歌 OGP画像」や「絶望おみくじ」を見て興味を持つ
   │
   ▼
[体験]   登録不要。エラーログを貼り付けるだけで、即座にAIが短歌とお焚き上げを実行
   │
   ▼
[拡散]   生成された美しい縦書きOGP画像をXにワンタップでシェア。「いいね」や共感を獲得
   │
   ▼
[継続]   毎日引ける「絶望おみくじ」、同じエラーに苦しんだ仲間が可視化される「同調バッジ」、
         自身の歴史が刻まれる「絶望年表（マイページ）」で習慣化
```

> 「このサービスは **エラー文に苦しむエンジニア** が、**悲痛な絶望を風流な短歌に変えて笑い飛ばせるようになる** サービス」

## 7. 実装機能一覧（本リリース実装済み）

### 🎋 AI短歌生成 ＆ AI法師の解脱助言

- **AI短歌自動生成**：エラーログをもとにOpenAI API（gpt-4o-mini）が哀愁漂う短歌を生成
- **モーラ数（音数）検証＆自動再生成ロジック**：ひらがな音数カウント＋±1音許容アルゴリズムによる自動フィードバックループ（最大3回）
- **AI法師の解脱助言**：ネタ化するだけでなく、絶望から救い出すための技術的な原因解説とアドバイスを「AI法師」が法話形式で伝授

### 🔥 クソコードのお焚き上げ

- 二度と見たくないバグコードを炎とともに浄化。絶望を昇華させる演出体験

### ⛩️ 本日の絶望おみくじ

- 運勢（大凶・極凶・絶望等）×エンジニアあるある絶望テーマをランダム判定
- 運勢別ビジュアル＆おみくじ短歌で毎日の習慣化を促進

### ⏳ 絶望年表（マイページ）

- ユーザーがこれまで直面してきたエラーと詠んだ短歌を「歴史の年表」のように時系列で振り返る重厚なタイムラインUI
- 総詠数・雅号（詠み手名）管理でログインユーザーの学習の足跡を蓄積

### 🎏 展覧会（Gallery）＆ 共感（いいね）・同調バッジ

- 和紙カード風ギャラリーで他のエンジニアの絶望短歌を一覧鑑賞
- Hotwire/Turboによる非同期ソート（新着順／共感数順）とリアルタイム「いいね」演出
- **同調バッジ**：同じエラー型を詠んだユーザー同士が可視化される、共感を形にする独自機能

### 🖼️ 動的縦書きOGP ＆ Xシェア

- MiniMagickによる短歌・雅号・背景のリアルタイム合成で「縦書き短歌カード」を動的生成
- ハッシュタグ「#絶望えらぁ短歌」と連携したXワンタップシェア機能

### 👤 ユーザー管理

- Deviseによるユーザー認証（ログイン・新規登録・雅号のマイページ自動反映）
- ゲストユーザー対応（登録なしでも即体験できるフロー設計）
- マイページから利用者自身でアカウント削除が可能

### 🎵 UX・和風世界観演出

- 完全縦書きUI（`writing-mode: vertical-rl`）で短冊に毛筆で書いたような表示
- 全画面怨念ローディング（「バグの神々の宣託を受信中…」等）
- 永続BGMプレイヤー：画面遷移（Turbo）しても再生が途切れない和風BGMコントローラー
- 漆黒漆塗り（#0d0808）×朱色ライン（#8c1d1d）で統一した重厚な和風ヘッダー・フッター

### 🛡️ セキュリティ・法的ガバナンス・CI/CD

- 利用規約・プライバシーポリシー（`/terms`, `/privacy`）を整備し、OpenAI APIへのデータ送信に関する注意喚起・著作権帰属・AI免責事項を明記
- `filter_parameter_logging` によりパスワード等の機密情報がサーバーログに平文出力されるのを防止
- GitHub Actions（CI/CD）によりPush／PR時に自動でRuboCop・Brakemanによる静的解析、`rails test` によるテストが走り、常時グリーンを維持

## 8. 技術的チャレンジと解決策：LLMは「音数」を数えられない

**課題**：LLMはトークン単位で言語を処理するため、日本語の「音数（読み）」の計算が極めて苦手です。指示通りに生成させても「5・8・5・7・8」のような字余り・字足らずが多発し、短歌としての美しさが損なわれるリスクがありました。

**解決アルゴリズム**：

```text
[エラーログ入力]
    │
    ▼
[OpenAI (gpt-4o-mini)] ──> { text: "...", kana: "あきらめて..." } をJSON出力
    │
    ▼
[Rails モーラ数検証ロジック]
    ├─① 拗音（「ゃ」「ゅ」「ょ」）を1音とみなして正確にカウント
    ├─② 各句が「5・7・5・7・7（±1音の字余り/字足らず）」に収まっているか判定
    │
    ├─【合格】──> [MiniMagickで縦書きOGP生成] ──> [完成・画面表示]
    │
    └─【不合格】─> [フィードバックプロンプト自動生成]
                       │（例：「3句目が8音でオーバーしています。修正してください」）
                       ▼
                  [OpenAIへ再リトライ（最大3回）]
                       │
                       └─【3回失敗時のトレードオフ意思決定】
                          冷たい定型文で逃げるのではなく、
                          「ユーザーの生の絶望ログに寄り添った生成歌」を優先して出力
```

LLM任せにせず、Rails側でロジックとして品質を担保する——ここに、AIを「使う」だけでなく「設計する」エンジニアリングの工夫が詰まっています。

## 10. 生成例

**【エラー】** `NoMethodError (undefined method 'tanka' for nil:NilClass)`

**【短歌】**
> ふたを開けて　出てくるのは　夢の欠片　空っぽコードに　涙も一緒

**【AI法師の解脱助言】**
「nilに対するメソッド呼び出しは、存在せぬ幻を追うがごとし。レシーバーが正しく生成されているか、存在チェックを行うのが悟りへの道でござる。」

---

**【エラー】** `Exception in thread "main" java.lang.NullPointerException at com.example.MyClass.doSomething`

**【短歌】**
> 意図せず　空の参照に　立ち尽くし　何もかもが消え　崩れ去る夢よ

**【AI法師の解脱助言】**
「NULLの参照は無常の嵐。変数に値が吹き込まれているか、nullチェックの結界を張るがよい。」

## 12. まとめ：なぜこのサービスが「個性」を体現するのか

「絶望えらぁ短歌」は、他の誰かの技術力ではなく、**自分自身が今まさにエラーと格闘してきたN=1の実体験**から生まれたプロダクトです。エラーという誰もが嫌うものを、短歌という日本の伝統文化と掛け合わせ、雅号・和風世界観・縦書きUIといった徹底した表現へ昇華させたのは、技術的な正解を追うのではなく「自分がどう表現したいか」を突き詰めた結果です。

エラーへの向き合い方も、それをアートに変える発想も、一人ひとり異なっていい——「絶望えらぁ短歌」は、その**個性を肯定するプロダクト**として、これからも初学者エンジニアの孤独に寄り添い続けます。
